# Public pull request → Astra repair → Daytona retest

The demo begins with [public PR #1](https://github.com/kllymx/gecco-rehearsals/pull/1).
It changes the actual app, session reader/writer and migration in Git. The coordinator reads the
PR's current base and head from GitHub, and records the exact commits before executing them.

The project, example app and validator are MIT licensed. GPT-6 Astra is the model service used
to generate the repair; its weights are not part of this repository. Running the cloud flow also
requires your own Daytona access and authenticated GitHub/Codex CLI installations.

## What the audience can inspect

1. The public PR and its code diff.
2. Two independent Daytona apps at the recorded base and head commits.
3. A successful isolated feature check followed by a reproduced compatibility failure.
4. A new commit generated by live GPT-6 Astra from those source files and failure observations.
5. A fresh pair at the same base and the exact published repair commit, running the same checks.

The PR stays open. The original commit, Astra's repair commit and the two rehearsal records remain
separate. This is a deliberately failing public example; it is not a claim that a production bug
was discovered or that another review tool missed it.

## Run

Follow [Daytona setup](DAYTONA.md). Keep your credentials in gitignored `.env.daytona` and add:

```sh
GECCO_DEMO_PR_URL=https://github.com/kllymx/gecco-rehearsals/pull/1
```

The coordinator host needs Git, GitHub CLI, Codex CLI and native PostgreSQL, with both `initdb`
and `postgres` on `PATH`. The validator creates disposable local databases before publishing;
it does not use an existing database service. On macOS, it sets `LC_ALL=C` in its restricted
environment so PostgreSQL can start reliably.

Sign in with `gh auth login`, then use `codex login` or configure the proxy below. The coordinator
uses these host credentials; they are never copied into the app sandboxes. The repair runner requests **gpt-6-astra** explicitly.
It uses the existing non-interactive Codex runner with structured output, tools disabled and no
filesystem access for the inference call. See [the official runner documentation](https://learn.chatgpt.com/docs/non-interactive-mode).

Build and start the coordinator, open **PR review & fix**, and choose **Run PR rehearsal**. After
an actual failed run, choose **Ask Astra to fix & rerun**. This action publishes the repair commit
to that PR branch after local validation, verifies deletion of the original sandboxes, and
starts a fresh pair. It does not merge the PR. If the current PR already passes, no fix is generated.

### Use an OpenAI-compatible proxy

To use a configured Responses endpoint, keep both settings in a private env file:

```sh
OPENAI_BASE_URL=https://your-proxy.example/v1
OPENAI_API_KEY=your-client-key
```

Restrict the file to your user (`chmod 600`) and set `GECCO_AI_ENV_FILE` in the coordinator's
gitignored `.env.daytona` to its absolute path. Alternatively, provide both variables directly
in the coordinator environment. The env file is read at each inference call and imports only
these two fields; it is never executed as a shell script.

The adapter selects an explicit Codex Responses provider using the configured base URL and key,
following the [official provider configuration](https://learn.chatgpt.com/docs/config-file/config-reference).
It preserves the requested `gpt-6-astra` model, leaves existing Codex sign-in unchanged, and rejects
incomplete configuration instead of switching authentication. The key stays in the host runner's
environment and is redacted before output can enter receipts. It is not copied to app sandboxes,
validation subprocesses, source commits or browser responses. HTTP and stream retries are disabled.

After changing coordinator environment settings, restart it before starting a fresh review.
The normal restart policy closes existing disposable sandbox pairs and retains their evidence.

Only same-repository PRs in `kllymx/gecco-rehearsals`, from `codex/demo-pr-*` into
`codex/demo-pr-base`, are accepted. This is the supported sample recipe, not arbitrary repository
onboarding. To repeat the original failure after PR #1 has been repaired, use a new sample branch
and PR at its original proposed commit; do not force-reset the repaired PR or remove its history.

## Execution and repair boundaries

- The base app keeps its own source. Both sandboxes separately load the exact proposed migration
  and SQL catalog from a checkout pinned to the PR head. The catalog checks statement digests
  across the database gateway; mismatched code cannot silently use the old query.
- Astra receives the base session contract, three proposed files and selected failure observations.
  The supplied compatible implementation is not included in the prompt. It produces full contents
  for `apps/fieldnotes/release.ts`, `deployment/up.sql` and `deployment/down.sql` only.
- The generated patch is constrained and checked in an isolated worktree. TypeScript checks and
  a coordinator-owned native PostgreSQL validator run before publication. The PR cannot change
  that validator, its expected session identities, or the visible new feature as part of the fix.
- A normal, non-forced push appends the fix only while the PR still matches the rehearsed source.
  A branch that changed during repair stops publication or retesting.
- The database observations determine the result. The model's explanation cannot mark a run
  passed. A repaired commit that still fails remains a failed result.
- The same seven-step journey tests the new feature, mixed rollout and newly written sessions.
  Native pre-publication validation additionally exercises rollback. The cloud main journey keeps
  v1 and v2 visible at rollout; cloud rollback is not implied by a seven-step passing result.
- Accepted work and operation intent are saved under gitignored `artifacts/reviews/`. Reload
  reconnects to it. An interrupted or uncertain inference, push or allocation is reconciled or
  reported inconclusive; it is not blindly repeated. A coordinator restart also invokes the
  existing cloud cleanup policy.
- A definite provider quota rejection with no returned patch allows a new explicit action after
  access is restored. The quota message remains visible and a private failure receipt is retained.
  This does not automatically retry inference or relax uncertain-operation handling.

## Validation record

The original public PR is based at `cac6057e2798e99905b91977fbfd9705f2c17758` and first proposed
`f4d4178e5686b1a22ea36c47ee7f62a4211d10a6`. Both commits passed root and standalone TypeScript checks.
The native proposal validator reproduced the original failure: isolated reads and feature saves
passed, while old-version reads failed during shared rollout and after rollback.

On September 10 at 20:01 UTC, the actual public PR completed all seven Daytona journey steps.
Both isolated reads and the new board's feature save passed. During shared rollout, the old app
failed with PostgreSQL error `42703`: `session_payload` no longer existed. The new app still read
and saved successfully. Both sandboxes reported the same proposed-source digest and exact PR head.
See the [recorded source and execution evidence](evidence/pr-1-original-proof.json).

The first repair request at 20:02 UTC hit the provider usage limit. After configuring an explicit
Responses endpoint and fixing the coordinator's native PostgreSQL locale, a fresh complete run
succeeded on September 10. Its original PR rehearsal reproduced the failure at 20:49 UTC. Live
GPT-6 Astra then generated three files from the exact source and observed failure. Root and
standalone TypeScript checks and all **15 immutable native PostgreSQL checks** passed before
[commit `5eff359`](https://github.com/kllymx/gecco-rehearsals/commit/5eff359d6f0a5fac3d1d814d286539ffb29a1bb8)
was appended to the same public PR.

Gecco verified deletion of both original sandboxes, created two fresh Daytona sandboxes at the
unchanged base and that exact repair commit, and completed **all seven rollout checks successfully**
at 20:51 UTC. The actual apps remained available side by side after the run. The PR is still open;
no merge was performed. See the [complete source, model, validation, cleanup and retest evidence](evidence/pr-1-astra-repair-proof.json).

This establishes the live PR-to-Astra-to-Daytona workflow for the supported sample. The model's
proposal said it had not run tests; the separate validator and subsequent Daytona run executed
after generation. Original failure records and failed setup attempts were retained separately.

The earlier [Daytona validation](DAYTONA.md#validation-scope) used the supplied compatible fixture
and must not be described as a generated repair.

A subsequent browser check toggled **Announce launch** in the repaired board and observed the
saved change in the old app through its normal polling, without a manual refresh. Only that
checkbox was restored; concurrent edits were preserved. See the [interaction receipt](evidence/pr-1-repaired-interaction-proof.json).

The original GitHub CI runs on `5eff359` exposed a legacy test wiring issue: the fixture test
loaded the repaired checkout reader but applied the bundled breaking migration. Those failed
runs remain visible. The live acceptance above used the exact committed reader **and** migrations.
The main-branch fixture tests and separate exact-proposal GitHub validation address these two
scopes independently; they do not relabel the original failed CI runs as passed.
